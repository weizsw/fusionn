# **大模型零幻觉双语字幕合并方案**

[https\://gemini.google.com/app/8b661f09d84f6497](https://gemini.google.com/app/8b661f09d84f6497)

*User prompt: 我现在一直用Duosubs 去将一个影视剧的中文的字幕和英文字幕合并成一个双语字幕 但现实是 这个合成出来的双语字幕 它的内容其实有的时候还是对应不上的 因为DuoSubs的本身的原理 它其实并不是说 能够像人一样去将两份字幕合并成一份双语字幕 因为即使是同一个影视剧 的中文和英文字幕 它们中间有些片段的时间轴其实还是有略微的差异的 然后导致它在合并的时候并不能非常完美的像人工一样的去将它合并成一份双语字幕 我现在想知道有没有什么更好的方法去做这个事情 我目前的想法是将这个合并的任务交给大模型去做 但是我不知道能否保证它的输入和输出能在其中不产生幻觉 然后引入更多的不是本身字幕的内容*

Response: 把双语字幕合并交给大模型来做，思路完全正确——**大模型在跨语言“意译识别”、“多对一断句缝合”以及“剔除无效噪音行”上的能力，远超传统工具。**

至于你最担心的“大模型产生幻觉、篡改原字幕内容或破坏时间轴”，在工程实现上有一个非常成熟且能做到 **100% 零文本幻觉** 的解法：**不要让大模型输出字幕文本，只让大模型做“连线题”（索引 ID 映射）。**

## **一、 为什么 DuoSubs 总是差点意思？**

知己知彼才能设计好替代方案。像 DuoSubs（哪怕它底层已经引入了 LaBSE 语义向量 \+ fastdtw 动态时间规整）这类工具之所以还是会频频错位，主要有三个算法死穴：

> 1. **一拆多 / 多合一的断句差异（1-to-N / N-to-1）：** 英文字幕受限于每行字符数和阅读速度，常把一个长句拆成两三段（例如第 1 段 Because if we don't,、第 2 段 everyone inside is going to die.）；而中文字幕习惯合成一句 因为如果我们不这么做，里面的人都得死。。单看前半句英文，语义向量残缺，传统算法算出来的余弦相似度极低，极易匹配失败。  
> 2. **非对白噪音引发的“骨牌式错位”（SDH 与注释）：** 英文字幕常带听障辅助标注（如 \[sighs\]、\[upbeat music playing\]），中文字幕则常有屏幕字翻译（如 【三天后】）或字幕组片头签名。传统的序列对齐算法（DTW）会强行寻找连续映射路径，一旦遇到单边多出来的“孤儿行”，往往会把前后两三句正常台词一起拉偏。  
> 3. **版本帧率与剪辑微差（Timeline Drift）：** 同一个剧集的 WEB-DL 版和 BluRay 版，或者不同流媒体源（Netflix vs AMZN），黑场转场时间可能差了 0.5 到 2 秒。当两份字幕时间轴本身没对齐时，任何依赖时间重叠窗口的启发式规则都会失效。

## **二、 核心解法：用“索引映射（Index Mapping）”彻底根除大模型幻觉**

如果你直接把两段 SRT 文本扔给大模型，让它“输出合并后的 SRT”，大模型在长文本生成时几乎必然会出现**漏词、擅自修改翻译、甚至把时间戳格式写坏**的情况。

**正确的工程架构是“算力与数据分离”：**

| 处理环节 | 负责角色 | 具体职责 | 是否有幻觉风险 |
| :---- | :---- | :---- | :---- |
| **1\. 解析与编号** | 本地脚本 (pysubs2) | 读取中英字幕，存入内存字典，赋予唯一编号 E1, E2... 和 C1, C2... | **0%**（纯确定性代码） |
| **2\. 语义对齐连线** | **大模型 (LLM)** | 只看编号、粗略秒数和文本，输出 JSON 格式的**编号对应关系**（例如 E10+E11 对应 C14） | **仅输出整数 ID，无法篡改任何原文字幕** |
| **3\. 校验与回填** | 本地脚本 (pysubs2) | 根据大模型返回的 ID 列表，直接从内存字典里取出**原汁原味的文本和时间戳**拼接生成 ASS/SRT | **0%**（纯确定性代码） |

### **具体流水线设计（5 步走）**

#### **第 1 步：用 alass 做物理级时间轴预对齐（关键前置动作）**

在把字幕交给任何合并程序前，强烈建议先跑一次开源工具 **alass**（Automatic Language-Agnostic Subtitle Synchronization）。

> * 不同于将字幕对齐到视频音轨的 ffsubsync，alass 支持**直接把副字幕（如中文）的时间轴对齐到主字幕（如英文）**：  
>   `alass english.srt chinese_raw.srt chinese_aligned.srt`

> * 它能基于动态规划在几秒内消除两份字幕之间的整体偏移、帧率微差（如 23.976 fps 与 24 fps）甚至商业广告黑场带来的分段偏移，把两份字幕的时间差收敛到毫秒级。

#### **第 2 步：投喂精简的“编号视图”给大模型**

不要把冗长的 00:01:12,450 \--\> 00:01:14,120 和 ASS 样式代码喂给大模型。只提取**行号、起止秒数（保留1位小数即可）、纯文本**：

`[English Track]`  
`E10 (72.4s-74.1s): Because if we don't do this right now,`  
`E11 (74.2s-76.0s): everyone in that building is dead.`  
`E12 (76.5s-77.8s): [sighs deeply]`  
`E13 (78.0s-79.5s): Make the call.`

`[Chinese Track]`  
`C14 (72.5s-76.1s): 如果我们现在不这么做，大楼里的人都得死。`  
`C15 (78.1s-79.4s): 打电话吧。`

#### **第 3 步：强制大模型输出 Structured Outputs（JSON Schema）**

利用大模型的结构化输出功能（Structured Outputs / JSON Schema），要求它只返回 ID 映射数组。当遇到断句不一致或单边噪音时，大模型能像人工校对一样轻松处理：

`{`  
  `"alignments": [`  
    `{ "en_ids": [10, 11], "zh_ids": [14], "type": "merge_en" },`  
    `{ "en_ids": [12],     "zh_ids": [],   "type": "en_only_sdh" },`  
    `{ "en_ids": [13],     "zh_ids": [15], "type": "1_to_1" }`  
  `]`  
`}`

> * **看到区别了吗？** 大模型返回的结果里**连一个中英文字母都没有**。它哪怕在极端情况下“犯糊涂”，最多也只是把数字 14 写成了 15，绝无可能凭空捏造一句台词或改写你原有的精校翻译。

#### **第 4 步：滑动窗口分块（Sliding Window）**

一集 45 分钟的美剧大约有 800～1200 行字幕。如果一次性全部塞进上下文，模型在后半程容易出现注意力衰减（漏行或编号滑移）。

> * **最佳实践：** 按时间轴每 **3～4 分钟（约 50～70 行）** 切成一个 Batch，相邻 Batch 之间留出 **15 秒的重叠区（Overlap）**，防止刚好卡在切分点上的跨句台词被强行截断。  
> * 使用轻量高速模型（如 gemini-2.5-flash 或本地跑量化版 Qwen），处理一整集只需十几个并发请求，耗时不到 10 秒，Token 消耗极低。

#### **第 5 步：代码侧的“防呆硬校验（Guardrails）”与合并策略**

拿到大模型返回的 JSON ID 映射后，由本地 Python 脚本执行三道铁律校验：

> 1. **时间窗防越界校验：** 检查配对的 en\_ids 与 zh\_ids 的时间戳差距。如果时间差大于设定的阈值（比如超过 8 秒），说明大模型胡乱连线了，代码直接拒绝该配对，回退到按时间戳就近插入。  
> 2. **完整性集合校验（防漏行）：** 用原字幕的 ID 集合减去大模型输出的 ID 集合（Missing\_IDs \= All\_IDs \- Mapped\_IDs）。任何被大模型遗漏的 ID，代码自动按原始时间戳原样塞回时间轴，保证**零丢行**。  
> 3. **多对一时间轴缝合规则：**  
   * 当 E10, E11 对应 C14 时，如果你更习惯以中文字幕的完整度为准，就把合成后的时间轴设为 min(E10.start, C14.start) 到 max(E11.end, C14.end)，英文行用空格拼接 E10.text \+ " " \+ E11.text，中文行直接取 C14.text。  
   * 如果你更希望严格保留英文原版的短句节奏，也可以只在 E10 和 E11 期间保持同一句 C14 持续显示。

## **三、 如果不想自己写代码，现有的工具还能怎么救？**

在动手写脚本之前，如果你正在使用的是开源的 **CK-Explorer/DuoSubs**（命令行或本地 Web UI 版），可以通过以下两个调整大幅改善它的对齐质量：

> 1. **更换底层语义向量模型与合并模式：** DuoSubs 默认使用的是较老的 sentence-transformers/LaBSE 模型，且默认工作在 synced 模式下（强依赖时间戳重叠过滤）。对于时间轴有微差、意译较多的影视剧，可以改用多语言语义表现好得多的 **Qwen/Qwen3-Embedding-0.6B** 或 **BAAI/bge-m3**，并将模式切换为 mixed：  
>    `duosubs merge -p english.srt -s chinese.srt --model Qwen/Qwen3-Embedding-0.6B --mode mixed`

> 2. **合并前先做正则去噪：** 无论是给 DuoSubs 还是其他对齐工具，事先用一行正则把英文字幕里的 

> $$.*?$$

> 3. 、\\(\[a-zA-Z\\s\]+\\)（听障提示音）以及 ^\[A-Z\\s\]+:（说话人前缀）清理掉，能直接消除 70% 以上的连续错位。

*User prompt: 在合并一拆多（如两句英文对应一句中文）的字幕时，怎么设计 ASS 双语字幕的时间轴起止策略和上下行字体样式最舒服？*

Response: 在处理“两句（或多句）英文对应一句中文”这类 **N-to-1 断句不一致** 的情况时，如果直接粗暴合并或者各自按原时间轴丢进 ASS 文件，很容易出现两个非常毁体验的问题：

> 1. **“字幕蹦迪”（垂直位置跳动）：** 播放器的 libass 渲染器默认具备防碰撞堆叠机制。如果中英分成两条独立 Dialogue 事件，当第一句英文结束、第二句英文还没出来的那 0.1 秒空隙里，原本被顶在上面的中文字幕会突然**掉到屏幕最底部**，0.1 秒后又被第二句英文**顶回去**，极其晃眼。  
> 2. **换行变成“三层汉堡”：** 如果无脑把两句长英文拼成一句，英文单行超过 70 个字符就会自动折成两行，加上中文字幕一共三行，瞬间遮挡画面下方的三分之一。

下面从时间轴起止策略（算法逻辑）**和**ASS 视觉排版工程（样式参数）两个维度，给出一套经过大屏观影检验的最佳实践方案。

## **一、 “一拆多”时间轴起止策略：自适应混合缝合法**

面对英文 E1 (72.4s \- 74.1s) \+ E2 (74.2s \- 76.0s) 对应中文 C1 (72.5s \- 76.1s) 的情况，最舒服的策略不是单一的“全拼”或“全拆”，而是让脚本根据**字符长度**和**句间停顿**做**自适应二选一**：

### **1\. 策略 A：整句缝合包络（适合短句、连贯台词）**

当两句英文原本就是被死板的字符限制拆开的同一个意群时，将它们合并成完整的一句英文，阅读体验最好（视线只需扫一次，也更利于对照听整句英语的连读和语调）。

> * **触发条件（需同时满足）：**  
  1. **总长度达标：** len(E1) \+ 1 \+ len(E2) \<= 65 个字符（保证 1080p 画布下英文绝不折行）。  
  2. **中间无明显停顿：** E2.start \- E1.end \<= 0.4秒（说明角色一直在连续说话，没有换气或镜头切换）。  
  3. **总跨度适中：** E2.end \- E1.start \<= 5.5秒（防止一句话在屏幕上挂太久提前剧透后半句）。  
> * **时间轴与文本合成规则：**  
  * **起止时间：** \[E1.start, E2.end\]（即 72.4s \--\> 76.0s）。  
  * **拼接方式：** 单条 Dialogue 事件，用空格拼接英文：  
    `Dialogue: 0,0:01:12.40,0:01:16.00,Default,,0,0,0,,如果我们现在不这么做，大楼里的人都得死。\N{\rEng}Because if we don't do this right now, everyone in that building is dead.`

### **2\. 策略 B：时间片切分 \+ 中文冻帧长驻（适合长句、带戏剧停顿的台词）**

如果 E1 \+ E2 拼起来有 90 个字符，或者角色说完前半句停顿了 1 秒才说后半句，强行拼在一起会导致英文折成两行。此时应该采用“中文视觉长驻，英文随语音翻页”的策略。

> * **如何做到“中文纹丝不动、英文平滑切换”？** 秘诀是**把这组字幕拆成两个无缝衔接的单事件时间片，并强行抹平中间的微小空隙**：  
  * **时间片 1：** E1.start 到 **E2.start**（注意：若 E2.start \- E1.end \< 0.5s，直接把第一段的结束时间拉长到 E2.start，彻底消除中间的黑场闪烁帧）。  
    * 显示内容：C1 \\N {\\rEng} E1  
  * **时间片 2：** **E2.start** 到 E2.end。  
    * 显示内容：C1 \\N {\\rEng} E2  
> * **视觉效果：** 在 72.4s 到 76.0s 的整段时间内，由于始终是同一个双行结构的 Dialogue 块在无缝替换，**上方的中文字幕在像素级位置上会像钉死在屏幕上一样完全静止**，只有下方的英文字幕在 74.2s 处干净利落地从前半句切换为后半句。

### **3\. 关键细节：时间轴究竟以英文还是中文为基准？**

在合并时间起止点时，**切忌无脑取并集 \[min(E.start, C.start), max(E.end, C.end)\]**。

> * **黄金法则是：永远以原版音轨对齐轨（通常是官方英文字幕）为绝对锚点。**  
> * 影视剧的原版 WEB-DL / BluRay 英文字幕通常经过严格的工业级打轴，其起止帧不仅精准贴合人声开口（Voice Onset），而且遵循了严格的**镜头切换避让原则（Scene-Cut Snap）**——不会跨越切镜多停留 0.2 秒导致闪一下。而民间中文字幕往往存在“晚出早退”或跨镜头拖尾的问题。因此，配对成功后的双语块，其起止时间戳直接取 \[E\_first.start, E\_last.end\] 观感最干净。

## **二、 ASS 双语字幕视觉工程：久看不累的样式设计**

在电视大屏（尤其是 OLED / HDR / 杜比视界环境）或桌面显示器上，默认播放器生成的纯白粗黑边字幕非常生硬且刺眼。一套舒服的 ASS 样式需要解决**主次分离、暗场护眼、跨行防粘连**三个问题。

### **1\. 上下排版与字号黄金比例**

根据观看目的不同，有两种主流范式（推荐默认采用第一种）：

| 维度 | 范式一：上中下英（主流观影 \+ 兼顾听力） | 范式二：上英下中（沉浸英语精听 / 跟读训练） |
| :---- | :---- | :---- |
| **位置逻辑** | **中文在上，英文在下**。人眼余光从画面中心往下扫时最先触达上行；且英文固定在最底部的黑边/安全区内，不会因英文长度变化改变中文的高度。 | **英文在上（字号略大或同大），中文在下（字号缩小且降低透明度）**。正常看剧只盯上行英文，听不懂某个俚语时眼球微移看一眼底部的半透明中文。 |
| **字号比例 (1080p 画布)** | 中文 52pt : 英文 36pt（约 **1.44 : 1**） | 英文 44pt : 中文 34pt |

### **2\. 色彩与 HDR 暗场护眼（告别纯白 \#FFFFFF）**

在支持 HDR 或高对比度的屏幕上，纯白（\&H00FFFFFF）会被激发到极高尼特亮度，在夜间暗场戏里非常晃眼。同时，中英两行如果同色，大脑需要多花 0.2 秒去区分语言边界。

**推荐两套久看不累的双语配色方案（注意 ASS 颜色格式为 \&HAABBGGRR，BGR 顺序与常规 RGB 相反）：**

> * **方案一：经典蓝光剧院风（雾白 \+ 暖杏金）—— 对比最鲜明**  
  * **主字幕（中文）：** 柔和雾白 \#EAECEF → ASS 值 \&H08EFECEA（带约 3% 微透明，柔化高光）  
  * **副字幕（英文）：** 暖杏浅金 \#E5C07B → ASS 值 \&H087BC0E5（比纯黄高级得多，温暖不刺眼，且与白字形成天然视觉分层）  
> * **方案二：现代极简冷调风（雾白 \+ 雾凇灰蓝）—— 最低画面干扰**  
  * **主字幕（中文）：** 柔和雾白 \#EAECEF → ASS 值 \&H08EFECEA  
  * **副字幕（英文）：** 雾凇灰蓝 \#B0BEC5 → ASS 值 \&H10C5BEB0（视觉权重自然退后一层，不抢戏，但盯看时依然锐利清晰）

### **3\. 字体选型：兼顾远距离易读性与跨设备渲染**

> * **中文字体：** 避免使用笔画有尖刺的宋体，也避免笔画过细的 Light 字重。  
  * 首选：**苹方-中黑 (PingFang SC Medium)**、**思源黑体 Medium (Source Han Sans SC Medium / Noto Sans CJK SC Medium)**，或偏人文温润感的 **霞鹜文楷 Medium (LXGW WenKai Medium)**。  
> * **英文字体：** 英文副字幕字号较小，必须选择 **x-height（小写字母高度）较大、字怀（Aperture）开阔** 的无衬线体，否则远看时 e / c / a / s 容易糊成一团。  
  * 首选：**Helvetica Neue Medium**、**Inter Medium**、**Roboto Medium** 或 **Trebuchet MS**（系统自带率高、识别度极佳）。

### **4\. 描边、阴影与防折行参数**

> * **画布锁定：** 必须在头部显式声明 PlayResX: 1920 和 PlayResY: 1080，否则不同播放器（如 Infuse、mpv、Emby、Kodi）对字号的缩放基准完全不一致。  
> * **WrapStyle 设为 2 或 0：**

## **一、 为什么会出现“一行英文对应多行中文”？**

在实际片源里，这种情况出现的频率仅次于“多英对一中”，主要有三种成因：

> 1. **国内字幕组/流媒体的“短句快切”习惯：** 英文字幕允许单条包含较长的复合句（甚至一条字幕里自带两行），而国内字幕规范倾向于“不加标点、按气口拆成短句”。  
   * E1 (10.0s \- 14.0s): I told you not to go there, but you never listen to me.  
   * C1 (10.1s \- 11.8s): 我叫你别去那儿  
   * C2 (12.0s \- 13.9s): 但你从来不听我的  
> 2. **单条英文包含双人对话，中文拆成了两条：** 英文字幕常把同一镜头内两人的快节奏一问一答塞进同一个字幕块（用换行和破折号区分），而中文字幕按两人开口的时间拆成了独立的两条。  
> 3. **中英倒装导致的“多对多交错”（M-to-N）：** 英文习惯“先果后因/状语后置”，中文习惯“先因后果/时间状语前置”。当一句话较长时，英文拆成了 E1, E2，中文拆成了 C1, C2，但 **E1 对应的其实是 C2，E2 对应的反而是 C1**。此时大模型会把它们打包成一个多对多集合：{"en\_ids": \[1, 2\], "zh\_ids": \[1, 2\]}。

## **二、 “一英对多中”的自适应策略（含时间轴锚定技巧）**

为什么“一英对多中”不能无脑合并中文？ 因为中文字符是方块字，字号又大（52pt）。在 1080p 画布下，一行中文如果超过 **26 个汉字** 就会触发自动折行。**一旦中文折成两行，屏幕下方就会出现“两行大号中文字 \+ 一行英文字”，压迫感比英文折行还要强烈得多。**

因此，脚本同样需要根据**合并后的汉字总字数**和**句间停顿**，做二选一自适应：

### **策略 A：中文空格缝合 \+ 严格锚定英文时间轴（占 80% 场景）**

当 C1 和 C2 只是被切碎的两个短分句时，合二为一最舒服。

> * **触发条件：**  
  1. 拼接后的中文字符总长度 **≤ 25 个字符**（确保 52pt 字号下绝对单行显示）。  
  2. 相邻中文字幕的空隙 **≤ 0.5 秒**。  
> * **合成规则：**  
  * **时间轴：** 直接采用 \[E1.start, E1.end\]，完全抛弃中文字幕原本略微不准的起止点，严格贴合原声。  
  * **文本拼接：** 用一个全角空格 拼接 C1 C2（如果检测到是双人对话，则格式化为 \- C1 \- C2）。

### **策略 B：“外框锁英文，内切借中文” \+ 英文冻帧长驻（长句或长停顿场景）**

当 C1 \+ C2 超过 25 个字（比如两个 16 字的长句），或者角色说完前半句停顿了 1 秒，中文就**绝对不能合并成一行**，必须让中文分两次翻页显示。

但这里有一个核心矛盾：**既然 E1 只有一条时间轴 \[10.0s, 14.0s\]，它并不知道句子中间的切分点在哪；如果我们又想坚持“以英文时间轴为基准”，该怎么切？**

答案是采用 **“外框锁英文，内切借中文”** 的混合锚定法：

> 1. **锁死外边界：** 整段话出现的起点锁死为 E1.start (10.0s)，消失的终点锁死为 E1.end (14.0s)——这样依然 100% 保留了官方英文字幕精准贴合人声开口和避让镜头切换（Scene-cut）的优势。  
> 2. **借用内部分割点：** 句中翻页的时间点 t\_split，直接借用第二句中文的起点 C2.start (12.0s)（并用代码限制 t\_split 必须落在 E1.start 和 E1.end 内部）。  
> 3. **无缝切片（消除中间闪烁）：**  
   * **时间片 1：** 10.0s → **12.0s**，显示 C1 \\N {\\rEng} E1  
   * **时间片 2：** **12.0s** → 14.0s，显示 C2 \\N {\\rEng} E1  
> * **最终视觉效果：** 在 10.0s 到 14.0s 期间，**底部的英文字幕 E1 像钉在屏幕上一样纹丝不动**；而上方的中文字幕在 12.0s 处干净利落地从 C1 切换成 C2，既不会挤成两行中文，又没有破坏英文原轨的起止边界。

## **三、 一个极易被忽略的隐形杀手：原生英文字幕的“内联换行”**

在讨论“一英对一中”或“一英对多中”时，有一个细节如果不处理，前面所有的字数控制都会失效：

**很多原版英文字幕（SRT），单条字幕块内部本身就是两行（带 \\n 换行符）！** 例如 Netflix 官方英文字幕严格限制每行不超过 42 个字符，所以哪怕只是一条 E1，它里面的文本长这样：

`Because if we don't do this right now,`  
`everyone in that building is dead.`

如果你直接读取 E1.text 塞进 ASS 的 \\N{\\rEng} 后面，哪怕它只是 1对1，在屏幕上也会渲染成 **1 行中文 \+ 2 行英文 \= 3 行字幕**。

**脚本预处理必做动作——内联换行展平（Unwrap Internal Newlines）：**

> * **普通句子：** 脚本在读取英文字幕入库时，先把单条字幕内部的 \\n 全部替换为空格 " "，拉平为一整句，然后再参与后面的 ≤ 65 字符长度判定。  
> * **单条内含双人对话：** 比如 E1 原文是：  
>   `- Are you sure?`  
>   `- Positive.`

>   如果总长度 ≤ 65 字符，脚本自动将其展平为单行双破折号格式：- Are you sure? \- Positive.（中间留 2～3 个空格），这样在 ASS 里依然只占底部薄薄的一行，极大释放画面空间。

| **4\. M EN : N ZH** | 语序倒装引发的多对多交错 | **双向缝合：** 中英各自拼接为单行，时间轴取 \[E1.start, Em.end\] | **按主轴重分配：** 若双边都太长无法合并，以 \[E1.start, Em.end\] 为外框，按英文时间片切分，并将中文字幕均摊或長驻显示 |

## **一、 单边字幕：三分法（去噪、留漏、顶路牌）**

既然我们要保留有意义的单边字幕，只需要让大模型在返回空配对（即 en\_ids: \[\] 或 zh\_ids: \[\]）时，顺带在 type 字段标一下它属于哪一类，脚本按类别做不同渲染：

| 单边类型 | 典型例子 | 大模型标记 (type) | 本地脚本处理策略 |
| :---- | :---- | :---- | :---- |
| **1\. 纯听障音效 (SDH)** | \[sighs\], (music playing), ♪ ... ♪ | sdh\_noise | **直接丢弃**，不写入最终 ASS，保持画面干净。 |
| **2\. 单边漏翻对白** | 英文有一句背景嘟囔 Watch out\!，中文字幕漏翻了 | orphan\_dialogue | **原样保留在屏幕底部**。只有英文就只用 Eng 样式渲染单行英文，不会留出空行。 |
| **3\. 屏幕字 / 路牌 / 剧集标题** | 画面出现英文报纸或 THREE DAYS LATER，英文轨为空，中文轨有 【三天后】 | sign\_or\_title | **保留中文字幕时间轴 \[C.start, C.end\]**。 • 若此时没人说话：正常显示在底部（或保持原字幕自带的位置标签）。 • **若此时刚好有人在说话（时间轴重叠）：脚本自动将这条路牌字幕顶到屏幕正上方（Top 样式，Alignment=8）**，绝不和底部的双语对话打架。 |

## **二、 重叠字幕（Overlapping）的三种工程解法**

在字幕文件里，两条字幕的时间轴发生重叠（即 Line\_A.end \> Line\_B.start），只有三种可能。我们在脚本里按以下优先级依次拦截处理：

### **1\. 第一种：伪重叠（打轴不严导致的 0.1s～0.4s 毫秒级踩踏）—— 脚本自动裁剪**

这是平时看剧最常见、也最毁体验的隐形 Bug。

> * **现象：** 角色说完第一句，紧接着说第二句。打轴的人手松了一点，导致第一句在 10.25s 结束，而第二句在 10.10s 就开始了（中间重叠了 0.15秒）。  
> * **如果不处理：** 在 10.10s \~ 10.25s 这短短零点几秒内，播放器发现有两条双语字幕同时存在，就会把第二条双语字幕**硬生生叠在第一条上面（瞬间变成 4 行字高）**，到了 10.25s 第一条消失，第二条又啪地一下掉回屏幕底部。  
> * **脚本解法（Overlap Snapping）：** 只要脚本检测到相邻两条**同轨道主对白**的重叠时间 **≤0.4秒**（或者重叠比例小于 25%），直接判定为“打轴手抖伪重叠”，强制执行 Line\_A.end \= Line\_B.start，把那 0.15 秒的重叠尾巴切齐。就这一行代码，就能消除 90% 莫名其妙的字幕上下乱跳。

### **2\. 第二种：主角说话 \+ 背景电视机/广播/画外音（主次双轨真重叠）—— 上下分屏路由**

当两条字幕重叠时间很长（比如重叠了 2 秒以上，或者一条长字幕完全包住了另一条短字幕），说明画面里真的有两个独立声源在同时发声（比如主角在吵架，背景电视机在播新闻；或者角色在说话，屏幕上弹出一条短信翻译）。

> * **怎么识别谁在上面、谁在下面？** 采用 **“原生标签优先 \+ 大模型语义兜底”** 的双重识别：  
  1. **原生标签识别（脚本层）：** 很多中文字幕或英文字幕原本就写了 {\\an8}（顶部居中）或 {\\pos(x,y)}。脚本在最初读取字幕时，不粗暴删掉 {\\an8}，而是给该行打上 is\_top \= True 的属性。  
  2. **大模型语义标记（LLM 层）：** 当大模型看到同一时间段有两路话同时出现时，它能轻易从语义上看出来哪句是剧情主对话（如 "Did you lock the door?"），哪句是电视新闻/广播/背景音/屏幕字（如 "Breaking news: The suspect is still at large..."），并在 JSON 中给背景音打上 "layer": "top"。  
> * **ASS 渲染效果：** 我们在 ASS 头文件里预设好一套 **TopDefault（顶部双语）** 样式，唯一区别就是把 Alignment 从 2（底部居中）改成 8（顶部居中）。  
  * **底部（Alignment=2）：** 正常播放主角的双语对话，按我们的策略 A/B 丝滑切换。  
  * **顶部（Alignment=8）：** 独立显示电视机新闻或路牌的双语/单语字幕。上下两条轨道各占屏幕一端，时间轴完全独立，互不干扰。

### **3\. 第三种：双人同时抢话（同级对话真重叠）—— 破折号并排合成**

如果同一秒钟重叠的两条字幕，既不是伪重叠，也不是背景电视机，而是两个角色面对面同时开口吵架/抢话：

> * E1 (10.0s \- 12.2s): You promised me\!  
> * E2 (10.3s \- 12.5s): I didn't have a choice\!  
> * **脚本解法：** 当检测到两条重叠超过 0.5 秒的字幕同属主对话（layer \== "bottom"）且各自字数都不长时，脚本自动将它们**合并进同一个时间窗口 \[min\_start, max\_end\]**，并在每句前自动补齐破折号 \- ，用全角空格横向并排拼接：  
>   `Dialogue: 0,0:00:10.00,0:00:12.50,Default,,0,0,0,,- 你答应过我的！ - 我当时没得选！\N{\rEng}- You promised me!   - I didn't have a choice!`

  * **如果两个人同时说的句子都特别长**（拼在一行里中文超过 26 字或英文超过 65 字符）：脚本才会退一步，将第一个人的双语放底部第 1 层，或者将后开口的人放到顶部/错开半秒切入，避免在底部堆出四行字。

## **三、 方案最终定型：全链路全景图**

把我们这几轮讨论的所有细节拼在一起，这套双语字幕合成方案的工程蓝图已经非常严密了：

> 1. **预处理层（本地脚本）：**  
   * *(可选)* 调用 alass 将中文字幕时间轴整体校准到英文字幕，消除片源版本偏移。  
   * 解析中英字幕，识别并记录原生顶部标签（{\\an8}），展平单条字幕内部的硬换行 \\n，剥离冗余 ASS 特效码，将纯净文本与精确毫秒时间戳锁入**本地只读字典**。  
> 2. **语义对齐层（大模型 Sliding Window \+ Structured JSON）：**  
   * 按 3～4 分钟一个窗口（带 15 秒重叠区）投喂轻量化编号视图 E1, E2... / C1, C2...。  
   * 大模型只输出 **ID 连线数组**（支持 1:1、N:1、1:N、M:N、单边保留、SDH 噪音丢弃 以及 top 背景音/路牌标记），**零文本输出 \= 零幻觉风险**。  
   * 对齐结果自动保存为本地 .map.json 缓存文件。  
> 3. **防呆校验与后处理排版层（本地脚本）：**  
   * **防呆校验：** 时间差越界拦截（防乱连线） \+ ID 集合差集补全（防漏行，漏掉的非噪音行自动按原时间轴归位）。  
   * **四象限自适应缝合：**  
     * N英 : 1中 → 短句（≤65字符且停顿$\leq 0.4s$）整句合并；长句按英文切片并让**中文冻帧长驻**（抹平小于 0.5s 的闪烁间隙）。  
     * 1英 : N中 → 短句（≤25汉字）空格合并；长句**外框锁英文起止、内切借中文起点**，让**英文冻帧长驻**。  
   * **重叠消解：** ≤0.4s 微小重叠自动裁剪对齐；背景电视/路牌路由至屏幕顶部 {\\an8}；双人同时抢话自动转单行双破折号 \- A \- B。  
> 4. **ASS 渲染输出层：**  
   * 输出 1080p 画布、柔化描边阴影、雾白+暖杏金/雾凇灰蓝配色的标准 .ass 文件。
